# ATAC-seq — FIXME

The one list of open work after v2.0.0. Compiled 2026-10-12 from the
open issues of `00.ISSUES.md` and the open findings of the ENCODE
review, `ENCODE_PIPE_CONCORDANCE.md`; both files are now in `attic/`.
Each entry gives its old ID: "was #N" for `attic/00.ISSUES.md`, "was
C-NN" for the review. Commits and docs written before this file use
those IDs. What ENCODE does, with its source files, is in
`attic/ENCODE_PIPE_CONCORDANCE.md` under the C-NN number.

- Architecture and conventions: `CLAUDE.md`
- What changed, per release: `CHANGELOG.md`
- Closed issues, with the reason: `attic/zzISSUES.md`

Labels: type (`bug`, `risk`, `docs`, `enhancement`, `cleanup`);
`encode` for a difference from the ENCODE ATAC-seq pipeline;
`pre-port` for a defect that existed under LSF and was carried over.
Entries are numbered in order of work, grouped by priority. Move a
closed entry to `attic/zzISSUES.md` with the reason.

Not carried over, because they are not open:

- C-01 to C-04, C-06, C-17: fixed in v2.0.0.
- C-07, the 30 bp insert filter: stays, and POST now also removes
  reads whose 5' end is soft-clipped. Both remove BWA-MEM's local
  alignments of reads that are not from the reference; removed for
  concordance, the insert filter let them make up 38-75% of the counts
  of ten Proj_18143 samples (`docs/SLURM_PORT.md`, "Insert-size and 5'
  clip filters").
- C-05, MAPQ 10 on BWA output: R. Koche's filter (`NOTES.md`); stays.
- C-08, supplementary alignments: PEMapper runs `bwa mem -M`, which
  writes none.
- C-09 (where duplicates are marked) and C-21 (aligner, trimming,
  reference): they come from PEMapper, which stays the mapper. The
  duplicate rate and NRF/PBC1/PBC2 are in #5. C-07 and C-02's
  `--keep-dup all` depend on C-21: the two read filters can be dropped
  only with an end-to-end aligner such as ENCODE's bowtie2, and
  without the 5' filter `--keep-dup all` lets the pileups of clipped
  reads into the peaks.

## Medium

**#32 `makeBigWigFromBEDZ.sh` sorts every read name for nothing** ·
`cleanup` `pre-port` — The 10M scale factor is set from
`zcat $BEDZ | cut -f4 | sort -S20g | uniq | wc -l`. `bedtools bamtobed`
appends `/1` and `/2` to paired read names, so every line of the
shifted BED has a distinct name and the count equals `wc -l` (checked
on the pre5 BEDs, 2026-10-13). The sort is most of the BW stage, the
slowest per GB (`RATE_BW=30`, CALLP 10), and is what sends full-size
BW jobs to the LONG queue. Fix: `count=$(zcat $BEDZ | wc -l)`, keep the
zero check, re-measure `RATE_BW` on the next full-size run and lower
`-M 24G` if the measured memory allows. The bigWig values do not
change. Found by the v2.0.0 primary-output review (atlas and bigWigs);
nothing else in those paths was found that is not already listed here.
Commit `79cb35e` added it as #30, a number #30 below already had.

**#5 No duplicate rate or library complexity** (was C-16; C-09) ·
`enhancement` `encode` — ENCODE reports the duplicate rate and the
library complexity (`lib_complexity.qc`); the pipeline reports
neither, so the complexity standards and ENCODE's depth standard (25
million non-duplicate, non-mitochondrial fragments) cannot be checked
from the delivery. The input BAMs have duplicates marked, not removed
(Picard MarkDuplicates in PEMapper), so both can be computed:

- Duplicate rate: `-f 1024` reads over mapped reads (`samtools
  flagstat` on the input BAM).
- NRF (distinct fragment positions / all fragments), PBC1 (positions
  seen once / distinct positions), PBC2 (positions seen once /
  positions seen twice), as ENCODE's `pbc_qc_pe`, on a name-sorted BAM
  that has passed the read filter but still has its duplicates:

  ```bash
  bedtools bamtobed -bedpe -i nmsrt.bam \
    | awk '{print $1,$2,$4,$6,$9,$10}' | grep -v "^chrM\s" | sort | uniq -c \
    | awk '... mt, m0, m1, m2, m0/mt (NRF), m1/m0 (PBC1), m1/m2 (PBC2)'
  ```

  Standards: NRF > 0.9, PBC1 > 0.9, PBC2 > 3. ENCODE's `grep` drops
  `chrM` only; use the `MITO` contig of `GENOMES.tsv` (`MT` on b37).

Fix: POST already name-sorts for `fixmate -r` (C-06), but drops the
duplicates first:

```bash
samtools view -u -q $MAPQ -f 3 -F 1804 -e "$KEEP_5P" $IBAM \
    | samtools sort -n ... | samtools fixmate -r - - \
    | samtools view -b -f 3 -F 1804 -e 'tlen > 30 || tlen < -30' ...
```

To reuse that sort, filter first with `-F 780` (1804 without the
duplicate bit), compute PBC from the `fixmate` output, and let the
second `-F 1804` drop the duplicates; this is ENCODE's order. The sort
then also handles the duplicates, so POST gets slower by about the
duplicate rate. Picard flags both reads of a duplicate pair, so the
postProcess BAM should not change. Check it on the downsampled hg38
test BAMs against a run of the current code: identical postProcess
BAMs and Check A exactly 1.0000. If a read of a pair is flagged without
its mate, it would be left as an orphan; then keep the current filter
and give PBC its own name sort instead. Write both metrics to
`out/<SID>/` and stage them to `atacSeq/metrics`. If the postProcess
BAM does change, `assignedCheck.sh` must still apply the same filter
(Check B relies on it).

**#6 "Fraction reads in peaks" is not ENCODE FRiP** (was C-11) ·
`enhancement` `encode` — `R/analyzeATAC.R` plots `Assigned / sum(all
status rows)` of the featureCounts summary: fragments over the
all-sample atlas divided by all fragments of the postProcess BAM,
`chrM` included. Other samples' peaks and the 500 bp merge inflate the
numerator, mitochondrial fragments the denominator, so it cannot be
judged against ENCODE's standard (FRiP > 0.3, > 0.2 acceptable).
ENCODE's FRiP is reads of the sample's tagAlign over its own filtered
peaks, divided by all its reads:

```bash
bedtools intersect -nonamecheck -a ta -b peaks -wa -u | wc -l   # over
wc -l ta                                                        # all
```

Fix: run this per sample on `*.shifted.bed.gz` and the sample's
`*_peaks.blacklistFiltered.narrowPeak`, write the result to
`out/<SID>/` and stage it to `atacSeq/metrics`. Relabel the existing
plots, titled "Mapped Reads in MACS Peaks" and "Fraction Reads in MACS
Peaks", as fragments in the atlas.

**#7 `___MITO.txt` is computed after filtering** (was C-10) ·
`enhancement` `encode` — POST counts `chrM` reads of the filtered BAM.
ENCODE's `frac_mito` uses unfiltered alignments (before the MAPQ,
proper-pair and duplicate filters). Mitochondrial reads are heavily
duplicated, so this fraction is lower than ENCODE's and the two are not
comparable. Fix: compute it from the input BAM with `samtools idxstats`
in POST (index the input first if it has no `.bai`); keep the
post-filter number too if wanted, under a different name. Related: the
postProcess BAM keeps `chrM` and every non-allowlisted contig, so
`CollectInsertSizeMetrics`, the featureCounts totals and the
`n_mapped_reads` column of the TSS CSV include them (the TSS score does
not). Either write a contig-filtered BAM for these metrics or document
it.

**#8 Other ENCODE QC metrics not produced** (was C-16) · `enhancement`

- Number of peaks per sample (`num_peak`), so a failed sample shows

**#13 The trap may not run during the R reports or staging** (was #8)

**#15 Old runs cannot be classified once `sacct` forgets the control

**#22 Fragment-length QC is a histogram only** (was C-15) ·
`enhancement` `encode` — ENCODE checks, from Picard
`CollectInsertSizeMetrics`: fraction of fragments under 150 bp >= 0.4;
NFR / mononucleosome (150-300 bp) >= 2.5; a peak in 20-90 bp, in
120-250 bp and in 300-500 bp, written as pass/fail lines. The pipeline
only plots the histogram (`plotINSStats.R`), so a sample without
nucleosomal periodicity is visible only to someone reading the PDF.
Fix: compute the five checks from the `___INS.txt` histogram and write

**#23 TSS enrichment details** (was C-14) · `bug` `encode` — Odd
read lengths: `tss_enrich.R` uses `SHIFT <- -read_len/2` (`-50.5` for
101 bp) and truncates per strand, giving `-51` on `+` and `+50` on
`-`. ENCODE uses integer division, `-51` on both strands. Fix:
`SHIFT <- -(read_len %/% 2)` for both strands; drop the truncation
comments in `tss_enrich.R` and update the shift sentences in
`R/TSSEnrich/README.md`, "Algorithm parameters". Even read lengths are
already exact. (The annotation version of the vendored TSS files,
GENCODE v24 / v19 / vM7 against ENCODE's current v3, is noted in
`docs/output.md` and `docs/methods.md` since v2.0.0.)

**#24 Tool versions are not recorded in the run** (was C-20) ·
`enhancement` `encode` — The versions are listed by hand in
`docs/methods.md` (MACS2 2.2.9.1, samtools 1.20, bedtools 2.31.1 and
Picard 3.4.0 from `~/bin`, wigToBigWig kent v361, bedClip v369) and

**#26 Tn5 shift has no guard against start >= end** (was C-19) ·
`cleanup` `encode` — ENCODE's `tn5_shift_ta` adds, after the +4/-5
shift, `if ($2 >= $3) { if ($6 == "+") {$2 = $3 - 1} else {$3 = $2 +
1} }`. The shift awk in `postMapBamProcessing_ATACSeq.sh` lacks it. It
cannot trigger on PEMapper BAMs (no BWA-MEM alignment is shorter than
its 19 bp minimum seed; Proj_18143 has many of 19-29 bp, so `-T 30`
does not bound it); add it for safety.

**#30 Ties at the 300,000 peak cap** · `cleanup` `encode` — In
`callPeaks_ATACSeq.sh` (`LC_ALL=C sort -k8,8gr`), peaks with equal
-log10 p are ordered by `sort`'s tie-breaking, which may differ from
ENCODE's. It matters only for a sample with more than 300,000 peaks
(four of the 15 in Proj_18143 v2.x-pre5), and only for which tied
peaks fall at the boundary.

**#31 `fixmate` compresses its output in POST** · `cleanup` — In
`postMapBamProcessing_ATACSeq.sh`, `samtools fixmate -r - -` has no
`-u`, so it compresses the stream the next `samtools view` reads.
Performance only; add `-u`.

**#33 `mergeSamples.sh` is undocumented** · `cleanup` `pre-port` —
`mergeSamples.sh MERGEID BED1,BED2,...` concatenates shifted BEDs and
sorts them into `merge_<MERGEID>__postProcess.shiftedPE.bed.gz`, for
pooling samples by hand. No doc mentions it, `pipe.sh` does not run it,
and no other file uses the `shiftedPE` name (the stages write
`*.shifted.bed.gz`). It has no usage block and no `pipefail`, so a
failed `zcat` or `sort` still exits 0, and it writes no `.md5`, so the
BW and CALLP stages cannot take its output. Decide whether to keep it:
if so, add a usage block, `set -eo pipefail` and the `.md5`, and
document it in `README.md`; if not, move it to `attic/`.

**#29 No reproducibility analysis** (was C-13) · `docs` `encode` —

pipeline uses the merged atlas and edgeR instead. Out of scope for a
count-matrix pipeline; IDR 2.0.3 is installed by `00.SETUP.sh` and
