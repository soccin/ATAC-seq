IRIS / Slurm only, as of v1.5.0. Compiled 2026-10-09 from a review of the
port and from probe jobs run on the cluster that day.

- Architecture and conventions: `CLAUDE.md`
- What changed, per release: `CHANGELOG.md`

  `docs/SLURM_PORT.md`

  `Proj_18143_B/PEMapper/docs/IRIS_CLUSTER_INFO.md`

Labels: type (`bug`, `risk`, `docs`, `enhancement`, `cleanup`), priority,

## Open

**#2 Partition and qos are not chosen per stage** · `bug` `high`
`port-gap` — The rule is: short partitions whenever possible, and
`--qos=priority` on the long partition. The control job follows it
through its `#SBATCH` directives. The stages have no mechanism for it.
`~/bin/bsub` picks the partition from `-W` (under two hours goes to
`cmobic_short,cpushort`, otherwise `cmobic_cpu`) but never sets a qos, so
a stage moved to `cmobic_cpu` runs at normal priority unless someone
remembers to add the qos by hand. The documented way to add it is wrong:
`CLAUDE.md` and `docs/SLURM_PORT.md` say to "export
`SBATCH_QOS=priority` for that call". `cpushort` allows only
`qos=normal`, and `EnforcePartLimits=ALL` is set, so a short-stage job
sent to `cmobic_short,cpushort` with priority qos is rejected
(`sbatch --test-only` on 2026-10-09: `Invalid qos specification`). If
the variable is exported in `pipe.sh`, or is already set in the shell
that submits the control job (it is passed through `--export=ALL`), every
later short `bsub` is rejected and the run aborts. Fix: in `pipe.sh`,
give each stage a class (SHORT or LONG) in one place. SHORT sets
`-W 1:59:00` and no qos. LONG sets the longer `-W` and
`SBATCH_QOS=priority` as a prefix on that `bsub` call only. Unset
`SBATCH_QOS` near the top of `pipe.sh`, and fix the two docs.

**#3 Stage walltimes dropped from 6 h to 1h59m** · `risk` `high`
`port-gap` — Under LSF, POST, BW, Count and TSSE ran with `-W 359`. Every
stage now has `-W 1:59:00` so that it fits `cpushort` (2 h hard limit).
Timing was measured only on 100x downsampled BAMs (about 1.2M reads; the
whole run took 5m38s). Before production use, do one full-size run, take
`Elapsed` per stage from `sacct` (the #1 manifest makes this direct), and
move any stage near two hours to the LONG class from #2.

**#4 Memory caps are estimates, and `sacct MaxRSS` cannot check them** ·
`risk` `medium` — Each `-M` is a hard cgroup cap; the values in
`docs/SLURM_PORT.md` were chosen, not measured. POST has the least
headroom: a 24g-heap picard plus the samtools/bedtools pipeline inside
32G. The control job (16G) runs `plotINSStats.R` and `analyzeATAC.R`
itself. As PEMapper found (its ISSUES #8), `MaxRSS` here counts page
cache, so do not lower a cap based on it. An `OUT_OF_MEMORY` state on the
full-size run (#3) is the signal to raise one.

**#5 A transient `squeue` failure aborts the run** · `bug` `medium` —
`~/bin/bSync.sh` runs `squeue ... 2>/dev/null` and treats empty output as
"all jobs done". If one `squeue` call fails (controller timeout), `bSync`
returns while the stage is still running. `bCheck` then retries for 60 s,
still sees `RUNNING`, counts that as a failure, and the run aborts. Fix in
`bin/slurmTools.sh`: while `sacct` shows any job of the group in an
active state, go back to `bSync` instead of failing; fail only on
terminal states other than `COMPLETED`. Smaller exposure of the same kind:
one rejected `bsub` submission aborts the run under `set -e`. A single
retry would cover a controller timeout.

**#6 Rerunning in the same analysis directory fails at the end** · `bug`
`medium` `pre-port` — `pipe.sh` lines 260, 263 and 264 call `mkdir`
without `-p` (`atacSeq/bigwig atacSeq/macs`, `out/metrics`, `out/bed`).
On a second run in the same directory every stage runs, then `set -e`
stops the control job at these lines, before anything is staged into
`atacSeq/`. Use `mkdir -p`. `out/postBams`, `out/metrics` and `out/bed`
are never written to and can be dropped.

**#7 Unsupported genomes are not rejected up front** · `bug` `medium`
`pre-port` — `pipe.sh` rejects only `unknown`. Detected tags such as
`hg19`, `b37_dmp` or `GRCh37-lite` pass, and then every POST job fails.
`mm10` is worse: stages 1 to 6 succeed, stage 7 (`computeTSSEnrich.sh`)
fails because `R/TSSEnrich/lib/` has only `b37` and `b38` files, and
`bCheck` aborts before anything is staged into `atacSeq/`. Only the first
BAM is checked, so mixed builds are not detected either. Fix: one
supported-genome check in `pipe.sh` over all BAMs. For mm10, add the TSS
files, or skip stage 7 with a warning when the files are missing.

**#8 `deliverResults.sh` not ported** · `enhancement` `medium` — Still

Delivery is manual until the script targets the IRIS delivery area.
When porting, check its file patterns against what
`R/diffAnalysisPairwise.R` writes now (`*DiffPeaksEdgeR_V4.xlsx`,

**#9 `~/bin/picard` is not sized from the Slurm job** · `enhancement`
`medium` — The wrapper is used as-is by POST. It sets a fixed `-Xmx24g`
whatever the job's `--mem` (POST asks for 32G to fit it). It puts
`TMP_DIR` on the shared `/scratch/core001/bic/socci/PICARD/$$` and never
removes that directory (101 empty directories there on 2026-10-09). Under
Slurm it also creates an empty `SLM/` in every analysis directory.
PEMapper already solved the first two: `TMP_DIR=/localscratch`, and the
heap derived from `SLURM_MEM_PER_NODE` in `bin/picardJvm.sh`. Decide
whether to fix the shared wrapper in `~/bin` or to reuse the PEMapper
approach inside this repo.

**#10 `sort` spills to the node's `/tmp`** · `enhancement` `low` —
`makeBigWigFromBEDZ.sh` (`sort -S20g`) and `mergePeaksToSAF.sh`
(`sort -S 16g`) do not set `-T` or `TMPDIR`, so anything beyond the
buffer goes to `/tmp` on the node. `/localscratch` is the node-local disk
meant for this.

**#11 Scratch directories are left behind on failure** · `cleanup` `low`
— `postMapBamProcessing_ATACSeq.sh` and `callPeaks_ATACSeq.sh` remove
their `$TDIR` under `/scratch/core001/bic/$USER/ATACSeq` only on success.
Add `trap 'rm -rf "$TDIR"' EXIT` after creating it.

**#12 A BAM without an `@RG SM:` tag writes into `out/`** · `bug` `low`
`pre-port` — `postMapBamProcessing_ATACSeq.sh` takes `SID` from the first
`SM:` tag. If there is none, `SID` is empty, the output becomes
`out/_postProcess.bam`, and samples processed in parallel overwrite each
other. Exit with an error when `SID` is empty. `pipe.sh` now checks every
BAM for an SM tag, and for duplicates, before submitting (#1), so this is
left only for standalone runs of the stage script.

**#13 `makeBigWigFromBEDZ.sh` scale-factor branch reads the wrong
argument** · `bug` `low` `pre-port` — With three arguments it sets
`scaleFactor=$2`, which is the BED path; it should be `$3`. `pipe.sh`
always passes two arguments, so the 10M-read normalization used in
production is not affected.

**#14 `featureCounts -Q 10` ignores `-q MAPQ`** · `bug` `low` `pre-port`
— The Count stage hard-codes `-Q 10`. With `-q` below 10, the count
matrix still uses 10. Pass `$MAPQ`.

**#16 `mkdir -p SLURM.CTRL` is not required** · `docs` `low` — Slurm

## Closed — fixed on `feat/runstatus` (not yet merged)

**#1 There is no reliable way to tell whether a run worked** — Done as
proposed. `pipe.sh` writes `00.RUNSTATUS.txt` (`STATUS=RUNNING`, then
`COMPLETED` after a per-sample deliverables check, or `FAILED` with
`STAGE`, `RC` and `MESSAGE` from the `EXIT` trap) and
`SLURM.CTRL/jobs.tsv` (job id, stage, sample, log), via the new `atacSub`
and `waitStage` helpers. Every stage job runs through `bin/runStage.sh`,
which ends the log with `#ATAC_EXIT=<rc>`. `bin/checkRun.sh` exits 0, 1 or
2 and reports a control job that died while the file still says
`RUNNING`. Exit-status fixes: `callPeaks_ATACSeq.sh` (`pipefail`, checked
filter step), `makeBigWigFromBEDZ.sh` (checked count and bigWig build),
`usage` exits 1. Tested 2026-10-09 on the 100x BAMs: a full run, a
cancelled stage job, a stage script exiting 1, `scancel` of the control
job, and SIGKILL of the control script.

**#17 Cancelling the control job leaves its stage jobs running** — The
cause was not what this entry said. On `scancel` Slurm sends SIGTERM to
the batch shell only, and bash runs a trap only after its foreground
child exits, so with `bSync.sh` in the foreground the trap never ran
before the SIGKILL 30 s later (test job 18357259). `bSync` now runs
`bSync.sh` in the background and `wait`s, which a trapped signal
interrupts; `onExit` cancels the run's jobs unless `RUN_DONE=1`, whatever
`$?` is. Verified with job 18357771: trap ran at once, `STATUS=FAILED
rc=143`, both stage jobs `CANCELLED`. During the R reports at the end of
`pipe.sh` the trap still may not run; `checkRun.sh` then reports the run
`FAILED` from `sacct`.

## Closed as by-design — do not "fix"

**#18 Dependence on `~/bin` and `~/.Rprofile`** — `sbatch`, `bsub`,
`bSync.sh`, `picard` and `bedtools` come from `~/bin`, and the R scripts
call `len()`, `cc()` and `DATE()` from `~/.Rprofile`. This was the user's
decision for the port. Consequence: only an account with these files can
run the pipeline.

**#19 Control job, not a dependency graph** — The user's decision. The
shim cannot express name-based `afterok` (Slurm needs numeric ids), so
`bSync`/`bCheck` sequencing replaces `-w post_done()`.

**#20 MD5 handshake with a 300 s retry** — Stays, per `CLAUDE.md`. The
consuming stages now start only after `bSync`, so the retry should rarely
trigger; a real mismatch costs five minutes.

**#21 One run per analysis directory** — Job names embed the control
job's pid, so runs in separate directories do not interfere. Two runs in
one directory share `out/` and collide.

**#22 Preemption** — Not a concern. `cmobic_cpu`, `cmobic_short` and
`cpushort` all have `PreemptMode=OFF` (checked 2026-10-09), so a job is
not requeued and restarted from the top.
